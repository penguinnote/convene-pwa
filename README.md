QR 코드로 설치하고, 운영진 공지를 전 참가자 폰에 실시간 푸시로 전달한다.
행사별 정체성은 설정 파일 하나로 분리해 다음 행사에 그대로 재사용한다.

## 1. 문제

책상에서 만든 문제 정의가 아니다. **이전 캠프를 직접 운영하며 같은 장면을 반복해서 봤고**, 임원진 회의와 참가자·운영진과의 대화에서 매년 같은 불만이 되풀이됐다. 정리하면 정보 전달이 세 갈래로 새고 있었다.

**① 공지가 묻힌다**
단체 카톡방은 알림을 꺼둔 사람이 많다. 공지를 올려도 읽힌다는 보장이 없고, 읽었더라도 이후 대화에 계속 밀려 내려가 정작 필요한 순간에 다시 찾기 어렵다. 운영진은 같은 공지를 몇 번씩 다시 올리게 된다.

**② 정보가 흩어진다**
일정은 인쇄물, 방배정은 엑셀 캡처, 말씀 본문은 또 다른 파일, 변경 사항은 카톡. 매체가 넷으로 쪼개져 있어 참가자가 매번 다른 곳을 뒤진다.

**③ 변경이 반영되지 않는다**
일정은 집회가 길어지면 뒤로 밀리고 식사가 당겨지면 앞으로 당겨진다. 그런데 이 변경이 실시간으로 공지되지 않고, 전달되더라도 이미 인쇄된 원래 일정표와 나란히 놓고 대조할 수가 없다. 결국 "지금 뭐 하는 순서인지"를 아는 유일한 방법은 옆 사람에게 묻는 것이다.

> **문제 정의** — 오프라인 행사의 흩어진 정보와 실시간 변경을, 참가자가 **한 곳에서 · 알림으로 · 네트워크가 끊겨도** 받게 한다.

## 2. 왜 설치형 PWA였나

문제를 풀려면 실시간 전달·정보 통합·오프라인 세 가지가 동시에 필요했다. 기존 대안은 각각 하나씩을 놓쳤다.

| | 실시간 전달 | 정보 통합 | 오프라인 | 설치 마찰 |
|---|---|---|---|---|
| 단체 카톡 | ○ | ✕ 스트림에 묻힘 | ✕ | ○ 이미 쓰고 있음 |
| 네이버 밴드 | △ 알림이 무시됨 | △ 게시판 수준 | ✕ | △ 가입 필요 |
| 인쇄물 | ✕ | △ 일부만 | ○ | ○ |
| 네이티브 앱 | ○ | ○ | ○ | ✕ 심사·용량·업데이트 |
| **설치형 PWA** | ○ | ○ | ○ | **△ QR 스캔 후 설치 단계** |

PWA도 완벽하지 않다. **설치 마찰이 △로 남았고, 실제로 그 △가 나중에 도달률의 병목으로 돌아왔다**(4장 참고). 다만 나머지 셋을 동시에 만족하면서 100명에게 강요할 수 있는 유일한 선택지였다.

## 3. 해결 — 문제와 해결과 검증의 연결

세 문제 각각에 해결책을 붙이고, **그 해결이 실제로 작동했는지 확인할 지표를 미리 정해뒀다.**

| 문제 | 해결 | 검증 결과 |
|---|---|---|
| ① 공지가 묻힌다 | 공지 전용 채널 + 작성 즉시 전원 푸시 + 상단 상시 노출 **고정 공지(자료 허브)** + 앱 사용 중엔 인앱 토스트 | **90명이 941회 열람** (참가자의 94%, 1인당 약 10회) · 공지 31건 발송 |
| ② 정보가 흩어진다 | 일정·방배정·말씀(한/영)·식단·플레이리스트·사진을 한 앱에 통합, 서비스워커로 오프라인 캐싱 | **4일간 화면 조회 8,221회 · 세션당 평균 5.1화면** — 한 번 열면 여러 정보를 이어서 봤다 |
| ③ 변경이 반영되지 않는다 | 라이브 "현재 순서" 시각 자동 계산 + 관리자 변동 메모 + 방배정·조 편성을 **재배포 없이** 폰에서 수정 | **라이브 링크 클릭 216회** (team 69 · verse 63 최다) · **관리자 5명**이 캠프 중 실제 운영 |

세부 기능은 [6장](#6-주요-기능), 이렇게 결정한 이유는 [CASE_STUDY.md](CASE_STUDY.md)에 있다.

## 4. 성과

캠프 **전에** 성공 지표를 정의하고, 캠프 **후에** 직접 만든 관리자 통계 대시보드로 채점했다. 결과는 섞여 있다.

![운영 지표](docs/camp_metrics_v4.png)

### 목표 대비 실제

분모를 둘 다 적었다. 이유는 바로 아래에서 설명한다.

| 지표 | 목표(사전) | 실인원 96명 기준 | uid 기준(대시보드) | 판정 |
|---|---|---|---|---|
| 공지 열람 | 정성적 "빠뜨리는 사람 없음" | **94%** (90/96) · 941회 | 73% (90/123) | ✅ 달성 |
| 푸시 권한 허용률 | ≥ 70% | **98%** (52/53) | 98% | ✅ 달성 |
| 4일 리텐션 (3일 이상 방문) | ≥ 60% | **71%** (68/96) | 39% (68/176) | ⚠️ 분모에 따라 뒤집힘 |
| 설치율 | ≥ 90% | **78%** (75/96) | 61% (75/123) | ❌ 미달 |
| 온보딩 완료율 | ≥ 90% | 산출 불가 | 69% (119/172) | ❌ 미달 |
| 조 편성 완료율 | ≥ 80% | 미산출 — 절대수 **56명** (R1 52 · R2 54 · R3 56) | 동일 | ❓ 분모 미기록 |

**보조 지표** 4일간 세션 1,616회 · 화면 조회 8,221회 · 공지 발송 31건 · 등록 토큰 60개 · 관리자 5명
**플랫폼** iOS 68 / Android 50 / 기타 5

### 발견 ① — 익명 로그인의 대가는 지표의 분모였다

실제 참가자는 등록 명단 기준 **96명**인데, 대시보드의 프로필 등록은 **123건**, 방문 uid는 **172개**다. 익명 로그인을 쓴 탓에 **재설치하거나 기기를 추가할 때마다 새 uid가 생기기** 때문이다. uid가 사람의 1.3~1.8배로 부풀어 있다.

그래서 같은 데이터가 분모에 따라 다른 결론을 낸다. 리텐션은 **uid 기준 39%, 실인원 기준 71%** — 목표 60% 앞뒤로 뒤집힌다. 온보딩 완료는 119건인데 실인원이 96명이라 애초에 "완료율"로 계산되지 않는다.

이건 측정 실수가 아니라 **제품 결정의 청구서**다. 100명에게 구글 로그인을 강요하지 않으려고 익명 로그인을 택했고([CASE_STUDY.md](CASE_STUDY.md) 결정 ④), 그 대가로 마찰 0을 얻는 대신 **사람 단위 지표를 잃었다.** 캠프가 끝나고 집계할 때야 드러났다.

다음 인스턴스에서는 uid와 사람을 잇는 최소 장치(설치 시 1회 코드 입력, 기존 프로필 복구 등)를 넣어야 한다. 로그인을 되돌리자는 게 아니라, **마찰을 늘리지 않으면서 분모를 되찾는 방법**을 찾는 것이다.

### 발견 ② — 푸시의 병목은 발송 로직이 아니라 설치였다

푸시 권한 **허용률 98%**와 도달률(토큰 보유) **63%** 사이에 큰 격차가 있다. 원인은 거부가 아니었다.

```
참가자 96명
  → 앱 설치 75명 (78%)
  → 푸시 권한 프롬프트 노출 53명       ← 여기가 병목
  → 허용 52명 (98%)
  → 푸시 토큰 보유 60개 (참가자의 63%)
```

iOS는 **홈 화면에 설치한 상태에서만** 푸시 권한을 요청할 수 있다. 프롬프트를 본 사람은 거의 다 허용했지만, 애초에 프롬프트까지 도달한 사람이 절반 남짓이었다. 알림을 못 받은 사람의 대부분은 **거부한 사람이 아니라 설치하지 않은 사람**이다.

허용률과 도달률을 **별개 지표로 분리해뒀기 때문에** 이걸 찾을 수 있었다. 하나의 "푸시 성공률"로 뭉갰다면 63%만 보고 발송 로직을 의심하며 엉뚱한 곳을 고쳤을 것이다. 실제 개선 과제는 설치 유도 온보딩이다.

### 발견 ③ — 1일차 이후 급감, 그리고 안 쓰인 기능

| 날짜 | DAU | 세션 | 화면 조회 |
|---|---|---|---|
| 7/29 (1일차) | 146 | 642 | 3,935 |
| 7/30 | 80 | 396 | 1,971 |
| 7/31 | 75 | 331 | 1,464 |
| 8/01 (4일차) | 66 | 247 | 851 |

화면 조회가 4일 만에 **78% 감소**했다. 일부는 자연스럽다 — 1일차에 방배정·일정·조 편성을 한 번에 확인하고 나면 이후엔 공지 위주로 짧게 쓰게 된다. 다만 감소 폭이 크고, 3일 이상 방문한 사람이 68명(71%)이라는 점을 함께 보면 **"매일 열 이유"를 만들지 못한 기능이 많았다**고 읽는 편이 정확하다.

라이브 링크 클릭 분포가 그 증거다.

| 링크 | 클릭 |
|---|---|
| team (조 편성) | 69 |
| verse (말씀 본문) | 63 |
| resource (자료 허브) | 34 |
| menu (식단표) | 27 |
| playlist | 19 |
| versesTab | 3 |
| schedule | **1** |

**schedule 1회, versesTab 3회** — 만들었지만 사실상 아무도 쓰지 않았다. 반면 조 편성과 말씀 본문이 상위였다. "지금 필요한 것"으로 바로 데려다주는 링크만 눌렸고, 이미 다른 탭에 있는 화면으로 가는 링크는 무의미했다. 다음엔 이 둘을 덜어내는 게 맞다.

## 5. 재사용 설계

행사마다 달라지는 값(앱 이름·표어·브랜드 색·외부 링크·시작일)을 **`src/config/instance.js` 한 파일**에 모았다. Tailwind 설정과 PWA 매니페스트가 이 파일을 함께 참조하므로, 새 행사에 배포하려면 이 파일만 교체하면 앱 전체의 이름·아이콘·테마 색·표어가 일괄 전환된다.

```js
export const INSTANCE = {
  appName: "2026 여름말씀캠프",
  org: "2026 로뎀나무교회 청년대학부 여름말씀캠프",
  slogan: "아담아, 네가 어디 있느냐?",
  liveAnchor: "2026-07-01",          // 라이브 '현재 순서' 계산 기준일
  theme: { palette: { /* ... */ }, manifestThemeColor: "#D3F0F3" },
};
```

## 6. 주요 기능

**참가자**

- **QR 설치형 PWA** — 앱스토어 없이 홈 화면 설치, 오프라인 캐싱으로 네트워크 불안정 환경에서도 열람
- **실시간 공지 푸시** — 관리자 작성 즉시 전원에게 백그라운드 알림. 앱 사용 중일 땐 시스템 알림 대신 인앱 토스트
- **라이브 "현재 순서"** — 지금·다음 순서를 자동 표시하고 관련 자료(말씀·식단·플레이리스트)로 바로 이동
- **말씀 본문** — 강의별 본문, 한글(개역개정)↔영어(NIV) 토글, 본문 글씨 크기 조절
- **일정 · 방배정 · 식단표 · 플레이리스트 · 사진**(Google Photos 공유 앨범 연동)
- **조 편성 게임** — 취향 질문 4개로 레크레이션 팀 배정, 서버 로직 없이 결정
- **참여자 디렉토리 · 목장** — 프로필 기반 참여자 목록
- **마이페이지** — 닉네임·목장·프로필 사진(크롭 지원) 관리
- **데스크톱 레이아웃** — 태블릿·노트북용 별도 셸(현장 안내 화면 대응)

**운영진**

- **리치 공지 에디터** — 텍스트·이미지·PDF·링크 블록을 순서대로 배치, 상단 상시 노출 **고정 공지(자료 허브)**
- **관리자 콘솔** — 공지 CRUD, 참여자 관리, 방배정 편집, 조 편성 관리, **운영 통계 대시보드**
- **무배포 실시간 편집** — 방배정·조 편성·라이브 메모를 폰에서 수정, 재배포 없이 전원 반영
- **권한 위임** — 임원 계정 추가로 여러 운영진이 콘솔 공유 (실제 5명이 사용)

**측정**

- 자체 이벤트 로그(`events` 컬렉션) + Google Analytics 4 병행. 설치·열람·온보딩·조 편성·공지 열람·라이브 링크 클릭·푸시 권한을 플랫폼·세션·일자와 함께 기록하고 관리자 대시보드로 집계

## 7. 아키텍처

![아키텍처](docs/architecture.png)

| 계층 | 구성 |
|---|---|
| DB | Firestore — 공지, 푸시 토큰, 사용자, 방배정, 이벤트 로그 |

## 8. 기술적으로 해결한 문제

### 플랫폼별 알림 동작 차이

- **iOS PWA 푸시 제약** — iOS는 16.4부터만 웹 푸시를 지원하고, 홈 화면에 설치한 앱으로 실행한 상태에서만 권한 요청·수신이 가능하다. 온보딩과 안내 문구를 이 제약에 맞춰 설계했다.
- **알림 클릭 이동** — iOS는 푸시를 탭하면 앱이 자동으로 열리지만 Android는 서비스워커의 `notificationclick` 핸들러가 있어야 동작한다. 핸들러를 추가해 양 플랫폼 동작을 통일했다.
- **iOS 앱 아이콘 배지** — Android는 자동 배지를 지원하지만 iOS는 Badging API로 직접 설정해야 해, 읽지 않은 공지 수를 `setAppBadge`로 표시하고 앱 진입 시 초기화했다.

### 서비스워커와 푸시 안정화

- **서비스워커 충돌** — vite-plugin-pwa의 기본 서비스워커와 FCM 서비스워커가 루트 스코프에서 충돌하는 문제를, `injectManifest` 전략으로 단일 서비스워커에 통합해 해결했다.
- **알림 중복·덮어쓰기 방지** — `data` 페이로드로 전환해 중복 표시를 막고, 알림마다 고유 `tag`를 부여해 여러 공지가 서로 덮어쓰지 않고 쌓이게 했다.
- **전달 우선순위** — webpush `Urgency: high` 헤더로 절전 상태에서도 즉시 전달되도록 했다.
- **즉시 갱신** — `skipWaiting` · `clientsClaim` · `cleanupOutdatedCaches`로 배포 후 앱 재실행만으로 새 버전이 적용되게 하고, 청크 로드 실패 시 자동 복구를 넣었다.
- **포그라운드/백그라운드 분리** — 백그라운드는 시스템 푸시, 포그라운드는 Firestore 구독 기반 인앱 토스트로 처리했다.

### 보안 — 익명 로그인 구조의 결함 발견

전원이 익명 로그인을 쓰는 구조 탓에 "로그인 여부"만으로는 관리자를 가릴 수 없어, **익명 사용자에게 관리자 화면이 노출되는 결함**이 있었다. UI 게이트를 이메일 보유 기준으로 바꾸고 Firestore 규칙에서 쓰기를 이메일 관리자로 제한해 **화면과 데이터 양쪽**을 막았다.

### 사용자 경험

- **계층적 뒤로가기** — Android 뒤로가기를 `popstate`로 가로채 도달 경로와 무관하게 지정된 부모 화면으로 보내고, 홈에서는 히스토리 누적을 제거해 종료 동작을 일관되게 만들었다.
- **Android WebAPK 설치 경고** — WebAPK의 `targetSdkVersion`이 낮으면 Play 프로텍트가 경고를 표시한다. 앱 코드로 제어할 수 없는 값이라 온보딩 안내로 대응했다.
- **긴 문자열 오버플로우** — 한글 줄바꿈용 `word-break: keep-all` 환경에서 띄어쓰기 없는 긴 문자열이 화면을 밀어내는 문제를 `overflow-wrap`으로 해결했다.
- **다이어그램 렌더링** — GitHub에서 Mermaid 렌더링이 불안정해 아키텍처 다이어그램을 PNG로 교체했다.

## 10. 회고

- **지표는 정의가 절반이다.** 리텐션이 분모에 따라 39%와 71% 사이에서 뒤집혔다. 숫자를 만드는 것보다 분모를 확정하는 게 먼저다.
- **제품 결정에는 측정 비용이 딸려 온다.** 익명 로그인으로 마찰 0을 샀지만, 그 대가로 사람 단위 지표를 잃었다. 결정할 때 "이 선택이 무엇을 못 보게 만드는가"를 같이 물었어야 했다.
- **병목은 기술이 아니라 온보딩일 수 있다.** 푸시 도달률의 한계는 발송 로직이 아니라 설치 완료율에 있었다. 지표를 분리해두지 않았다면 엉뚱한 곳을 고쳤을 것이다.
- **"동작한다"는 한 기기의 착각이다.** 상태바·설치·배지·알림 클릭·WebAPK 경고 등 OS별 동작 차이가 커서, 실기기 교차 검증 없이는 아무것도 확신할 수 없었다.
- **안 쓰인 기능을 세는 게 쓰인 기능을 세는 것만큼 중요하다.** schedule 링크는 4일간 1번 눌렸다. 만들기 전에 알 수 있었을까를 되묻게 된다.
- **트레이드오프를 문서로 남기니 결정이 빨라졌다.** 라이브 카드처럼 세 번 되돌아온 결정도, 근거가 적혀 있으면 재논의 비용이 낮다.

## 13. 다음 개선

데이터에서 나온 순서대로다.

1. **uid ↔ 사람 매핑 복구** — 마찰을 늘리지 않으면서 분모를 되찾는다. 설치 시 1회 코드 입력이나 기존 프로필 복구 흐름을 검토한다. 이게 안 되면 다음 캠프의 지표도 같은 이유로 흔들린다.
2. **설치 유도 온보딩 강화** — 설치율 78%, 푸시 프롬프트 노출 55%가 병목이다. 첫 진입 시 설치 안내를 강제 단계로 올리고 미설치 상태를 감지해 재안내한다. 목표: 도달률 85%.
3. **안 쓰인 링크 정리** — 라이브 카드의 `schedule`·`versesTab` 링크를 덜어낸다.
4. **측정 분모 선확정** — 지표 정의서에 분자·분모·이벤트명을 함께 적고 이벤트를 심는다.
5. 일정·식단 등 나머지 정적 데이터도 관리자 페이지에서 실시간 편집하도록 확장한다.
6. GitHub Actions 기반 CI/CD 자동 배포를 구성한다.
