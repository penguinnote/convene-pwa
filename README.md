**다중일 오프라인 행사(워크숍·수련회·캠프)용 설치형 컴패니언 PWA**

## 1. 문제

이 문제 정의는 이전 캠프를 직접 운영하며 반복적으로 관찰한 내용과, 임원진 회의 및 참가자·운영진과의 대화에서 매년 제기된 사항을 근거로 한다. 정보 전달의 문제는 세 가지로 정리된다.

**① 공지가 묻힌다**
단체 카톡방은 알림을 꺼둔 참가자가 많아 공지의 도달 자체가 보장되지 않는다. 확인한 경우에도 이후 대화에 밀려 내려가 필요한 시점에 다시 찾기 어렵다. 이로 인해 운영진은 동일한 공지를 반복해서 게시하게 된다.

**② 정보가 흩어진다**
일정은 인쇄물, 방배정은 엑셀 캡처 이미지, 말씀 본문은 별도 파일, 변경 사항은 메신저로 전달된다. 매체가 네 갈래로 나뉘어 있어 참가자가 정보를 확인할 때마다 다른 경로를 거쳐야 한다.

**③ 변경이 반영되지 않는다**
집회가 길어지면 일정이 지연되고, 식사 시간이 조정되면 앞당겨진다. 그러나 이러한 변경이 실시간으로 전달되지 않으며, 전달되더라도 이미 배포된 원래 일정표와 대조할 수단이 없다.

> **문제 정의** — 오프라인 행사의 분산된 정보와 실시간 변경 사항을, 참가자가 **단일 경로에서 · 알림을 통해 · 네트워크 연결이 불안정한 환경에서도** 확인할 수 있게 한다.

## 2. 왜 설치형 PWA였나

문제 해결에는 실시간 전달·정보 통합·오프라인 접근이 동시에 필요했다. 기존 대안은 각각 하나 이상의 조건을 충족하지 못한다.

| | 실시간 전달 | 정보 통합 | 오프라인 | 설치 마찰 |
|---|---|---|---|---|
| 단체 카톡 | ○ | ✕ 스트림에 묻힘 | ✕ | ○ 이미 사용 중 |
| 네이버 밴드 | △ 알림 확인율 낮음 | △ 게시판 수준 | ✕ | △ 가입 필요 |
| 인쇄물 | ✕ | △ 일부만 | ○ | ○ |
| 네이티브 앱 | ○ | ○ | ○ | ✕ 심사·용량·업데이트 |
| **설치형 PWA** | ○ | ○ | ○ | **△ QR 스캔 후 설치 단계** |

PWA 역시 완전한 해법은 아니다. **설치 마찰이 △로 남았고, 이 항목이 실제 운영에서 푸시 도달률의 제약으로 작용했다**(4장 참고). 다만 나머지 세 조건을 동시에 충족하면서 100명 규모에 적용하기에는 가장 적합한 선택지로 판단했다.

## 4. 성과

캠프 시작 전에 성공 지표를 정의하고, 종료 후 직접 구축한 관리자 통계 대시보드로 측정했다. 결과는 항목별로 달랐다.

![운영 지표](docs/camp_metrics_v4.png)

### 목표 대비 실제

분모를 두 가지로 병기했다. 사유는 아래에서 설명한다.

| 지표 | 목표(사전) | 실인원 96명 기준 | uid 기준(대시보드) | 판정 |
|---|---|---|---|---|
| 공지 열람 | 정성 목표 "미확인자 없음" | **94%** (90/96) · 941회 | 73% (90/123) | ✅ 달성 |
| 푸시 권한 허용률 | ≥ 70% | **98%** (52/53) | 98% | ✅ 달성 |
| 4일 리텐션 (3일 이상 방문) | ≥ 60% | **71%** (68/96) | 39% (68/176) | ⚠️ 분모에 따라 판정 상이 |
| 설치율 | ≥ 90% | **78%** (75/96) | 61% (75/123) | ❌ 미달 |
| 온보딩 완료율 | ≥ 90% | 산출 불가 | 69% (119/172) | ❌ 미달 |
| 조 편성 완료율 | ≥ 80% | 미산출 — 절대수 **56명** (R1 52 · R2 54 · R3 56) | 동일 | ❓ 분모 미기록 |

**보조 지표** 4일간 세션 1,616회 · 화면 조회 8,221회 · 공지 발송 31건 · 등록 토큰 60개 · 관리자 5명
**플랫폼** iOS 68 / Android 50 / 기타 5

### 익명 로그인 선택이 지표 산출에 미친 영향

등록 명단 기준 실제 참가자는 **96명**이나, 대시보드상 프로필 등록은 **123건**, 방문 uid는 **172개**로 집계됐다. 익명 로그인 방식에서는 재설치하거나 기기를 추가할 때마다 새 uid가 생성되기 때문이다. uid 수가 실인원의 1.3~1.8배 수준이다.

이로 인해 동일한 데이터가 분모에 따라 다른 결과를 산출한다.

- **리텐션** — uid 기준 39%, 실인원 기준 71%. 목표치 60%를 기준으로 판정이 뒤바뀐다.
- **온보딩 완료** — 119건으로 실인원 96명을 초과하므로 완료율을 산출하기 어렵다.
- **설치율** — uid 기준 61%, 실인원 기준 78%. 어느 기준으로도 목표에 미달하나 격차가 17%p다.

이는 측정 과정의 오류가 아니라 제품 결정에 수반된 비용이다. 참가자 전원에게 구글 로그인을 요구하지 않기 위해 익명 로그인을 유지했고([CASE_STUDY.md](CASE_STUDY.md) 결정 ④), 그 결과 진입 마찰을 제거하는 대신 사람 단위 지표를 확보하지 못했다. 이 비용은 결정 시점에 고려되지 않았으며 캠프 종료 후 집계 단계에서 확인됐다.

다음 인스턴스에서는 uid와 개인을 연결하는 최소한의 장치(설치 시 1회 코드 입력, 기존 프로필 복구 등)가 필요하다. 로그인 방식을 변경하는 것이 아니라, 진입 마찰을 늘리지 않으면서 분모를 확보하는 방법을 검토한다.

### 푸시 도달률 저하의 원인

푸시 권한 **허용률 98%**와 도달률(토큰 보유) **63%** 사이에 큰 차이가 있다. 퍼널을 단계별로 확인한 결과 권한 거부가 주된 원인은 아니었다.

```
참가자 96명
  → 앱 설치 75명 (78%)
  → 푸시 권한 프롬프트 노출 53명       ← 제약 지점
  → 허용 52명 (98%)
  → 푸시 토큰 보유 60개 (참가자의 63%)
```

iOS는 홈 화면에 설치한 상태에서만 푸시 권한을 요청할 수 있다. 프롬프트가 노출된 사용자는 대부분 권한을 허용했으나, 프롬프트 노출 단계까지 도달한 인원이 절반 수준에 그쳤다. 알림을 수신하지 못한 인원의 다수는 권한을 거부한 사용자가 아니라 앱을 설치하지 않은 사용자다.

허용률과 도달률을 별개 지표로 정의했기 때문에 이 원인을 식별할 수 있었다. 두 지표를 하나로 통합했다면 63%라는 수치만 확인하고 발송 로직을 원인으로 판단했을 가능성이 높다. 실제 개선 과제는 설치 유도 온보딩이다.

### 일자별 사용량 추이와 기능별 활용도

| 날짜 | DAU | 세션 | 화면 조회 |
|---|---|---|---|
| 7/29 (1일차) | 146 | 642 | 3,935 |
| 7/30 | 80 | 396 | 1,971 |
| 7/31 | 75 | 331 | 1,464 |
| 8/01 (4일차) | 66 | 247 | 851 |

화면 조회 수가 4일간 **78% 감소**했다. 1일차에 방배정·일정·조 편성을 집중적으로 확인한 뒤 이후에는 공지 중심으로 짧게 사용하는 패턴은 자연스러운 측면이 있다. 다만 감소 폭이 크고, 3일 이상 방문자가 68명(71%)이라는 점을 함께 고려하면 재방문 동기를 제공하지 못한 기능이 다수 존재했다고 판단한다.

라이브 링크 클릭 분포가 이를 뒷받침한다.

| 링크 | 클릭 |
|---|---|
| team (조 편성) | 69 |
| verse (말씀 본문) | 63 |
| resource (자료 허브) | 34 |
| menu (식단표) | 27 |
| playlist | 19 |
| versesTab | 3 |
| schedule | **1** |

`schedule` 링크는 4일간 **1회**, `versesTab`은 3회 클릭됐다. 반면 조 편성과 말씀 본문이 상위를 차지했다. 현재 필요한 정보로 직접 이동하는 링크만 사용됐고, 하단 탭에서 이미 접근 가능한 화면으로 연결되는 링크는 활용되지 않았다. 다음 인스턴스에서는 해당 링크를 제거하는 것이 적절하다.

## 5. 재사용 설계

행사마다 달라지는 값(앱 이름·표어·브랜드 색·외부 링크·시작일)을 **`src/config/instance.js` 단일 파일**에 모았다. Tailwind 설정과 PWA 매니페스트가 이 파일을 참조하므로, 새 행사에 배포할 때 이 파일만 교체하면 앱 전체의 이름·아이콘·테마 색·표어가 일괄 전환된다.

```js
export const INSTANCE = {
  appName: "2026 여름말씀캠프",
  org: "2026 로뎀나무교회 청년대학부 여름말씀캠프",
  slogan: "아담아, 네가 어디 있느냐?",
  liveAnchor: "2026-07-01",          // 라이브 '현재 순서' 계산 기준일
  theme: { palette: { /* ... */ }, manifestThemeColor: "#D3F0F3" },
};
```

## 6. 주요 기능

**참가자**

- **QR 설치형 PWA** — 앱스토어 심사 없이 홈 화면 설치, 오프라인 캐싱으로 네트워크 불안정 환경에서도 열람 가능
- **실시간 공지 푸시** — 관리자 작성 즉시 전원에게 백그라운드 알림. 앱 사용 중에는 시스템 알림 대신 인앱 토스트
- **라이브 "현재 순서"** — 현재·다음 순서를 자동 표시하고 관련 자료(말씀·식단·플레이리스트)로 이동
- **말씀 본문** — 강의별 본문, 한글(개역개정)↔영어(NIV) 토글, 본문 글씨 크기 조절
- **일정 · 방배정 · 식단표 · 플레이리스트 · 사진**(Google Photos 공유 앨범 연동)
- **조 편성 게임** — 취향 질문 4개로 레크레이션 팀 배정, 서버 로직 없이 클라이언트에서 결정
- **참여자 디렉토리 · 목장** — 프로필 기반 참여자 목록
- **마이페이지** — 닉네임·목장·프로필 사진(크롭 지원) 관리
- **데스크톱 레이아웃** — 태블릿·노트북용 별도 셸(현장 안내 화면 대응)

**운영진**

- **리치 공지 에디터** — 텍스트·이미지·PDF·링크 블록을 순서대로 배치, 상단 상시 노출 **고정 공지(자료 허브)**
- **관리자 콘솔** — 공지 CRUD, 참여자 관리, 방배정 편집, 조 편성 관리, **운영 통계 대시보드**
- **무배포 실시간 편집** — 방배정·조 편성·라이브 메모를 모바일에서 수정, 재배포 없이 전원 반영
- **권한 위임** — 임원 계정 추가로 복수 운영진이 콘솔 공유 (실제 5명 사용)

**측정**

- 자체 이벤트 로그(`events` 컬렉션) 및 Google Analytics 4 병행. 설치·열람·온보딩·조 편성·공지 열람·라이브 링크 클릭·푸시 권한을 플랫폼·세션·일자와 함께 기록하고 관리자 대시보드에서 집계

## 8. 기술적으로 해결한 문제

### 플랫폼별 알림 동작 차이

- **iOS PWA 푸시 제약** — iOS는 16.4부터 웹 푸시를 지원하며, 홈 화면에 설치한 앱으로 실행한 상태에서만 권한 요청·수신이 가능하다. 온보딩과 안내 문구를 이 제약에 맞춰 설계했다.
- **알림 클릭 이동** — iOS는 푸시를 탭하면 앱이 자동으로 실행되나 Android는 서비스워커의 `notificationclick` 핸들러가 필요하다. 핸들러를 추가해 양 플랫폼 동작을 통일했다.
- **iOS 앱 아이콘 배지** — Android는 자동 배지를 지원하나 iOS는 Badging API로 직접 설정해야 하므로, 미확인 공지 수를 `setAppBadge`로 표시하고 앱 진입 시 초기화했다.

### 서비스워커와 푸시 안정화

- **서비스워커 충돌** — vite-plugin-pwa의 기본 서비스워커와 FCM 서비스워커가 루트 스코프에서 충돌하는 문제를 `injectManifest` 전략으로 단일 서비스워커에 통합해 해결했다.
- **알림 중복·덮어쓰기 방지** — `data` 페이로드로 전환해 중복 표시를 방지하고, 알림마다 고유 `tag`를 부여해 복수 공지가 서로 덮어쓰지 않도록 했다.
- **전달 우선순위** — webpush `Urgency: high` 헤더를 적용해 절전 상태에서도 즉시 전달되도록 했다.
- **즉시 갱신** — `skipWaiting` · `clientsClaim` · `cleanupOutdatedCaches`를 적용해 배포 후 앱 재실행만으로 새 버전이 반영되게 하고, 청크 로드 실패 시 자동 복구를 추가했다.
- **포그라운드/백그라운드 분리** — 백그라운드는 시스템 푸시, 포그라운드는 Firestore 구독 기반 인앱 토스트로 처리했다.

### 보안 — 익명 로그인 구조의 결함

전원이 익명 로그인을 사용하는 구조에서는 로그인 여부만으로 관리자를 구분할 수 없어, **익명 사용자에게 관리자 화면이 노출되는 결함**이 있었다. UI 게이트를 이메일 보유 기준으로 변경하고 Firestore 규칙에서 쓰기 권한을 이메일 관리자로 제한해 **화면과 데이터 양쪽**에서 접근을 차단했다.

### 사용자 경험

- **계층적 뒤로가기** — Android 뒤로가기를 `popstate`로 가로채 도달 경로와 무관하게 지정된 상위 화면으로 이동시키고, 홈에서는 히스토리 누적을 제거해 종료 동작을 일관되게 처리했다.
- **Android WebAPK 설치 경고** — WebAPK의 `targetSdkVersion`이 낮으면 Play 프로텍트가 경고를 표시한다. 앱 코드로 제어할 수 없는 값이므로 온보딩 안내로 대응했다.
- **긴 문자열 오버플로우** — 한글 줄바꿈을 위한 `word-break: keep-all` 환경에서 공백 없는 긴 문자열이 레이아웃을 밀어내는 문제를 `overflow-wrap`으로 해결했다.
- **다이어그램 렌더링** — GitHub의 Mermaid 렌더링이 불안정해 아키텍처 다이어그램을 PNG로 교체했다.

## 10. 회고

- **지표를 정의할 때 분모를 함께 확정해야 한다.** 리텐션이 분모에 따라 39%와 71%로 갈렸다. 목표치를 설정하는 작업과 계산 가능한 형태로 로깅하는 작업은 별개다.
- **제품 결정에는 측정 비용이 수반된다.** 익명 로그인으로 진입 마찰을 제거했으나 사람 단위 지표를 확보하지 못했다. 결정 시점에 해당 선택이 어떤 관측을 어렵게 만드는지 함께 검토했어야 한다.
- **성능 제약이 기술이 아닌 온보딩에 있을 수 있다.** 푸시 도달률의 한계는 발송 로직이 아니라 설치 완료율에서 발생했다. 지표를 분리하지 않았다면 원인을 잘못 진단했을 가능성이 있다.
- **단일 기기 검증은 충분하지 않다.** 상태 표시줄, 설치 절차, 배지, 알림 클릭, WebAPK 경고 등 OS별 동작 차이가 커 실기기 교차 검증이 필요했다.
- **사용되지 않은 기능의 측정도 동일하게 중요하다.** `schedule` 링크는 4일간 1회 클릭됐다. 클릭 로그가 없었다면 확인하기 어려운 사실이다.
- **의사결정 근거를 문서화하면 재논의 비용이 낮아진다.** 라이브 카드처럼 세 차례 방향을 변경한 결정도 근거가 기록돼 있으면 재검토가 빠르다.

## 13. 다음 개선

측정 결과에 근거한 우선순위다.

1. **uid ↔ 개인 매핑 확보** — 진입 마찰을 늘리지 않으면서 분모를 확보한다. 설치 시 1회 코드 입력 또는 기존 프로필 복구 흐름을 검토한다. 이 문제가 해결되지 않으면 다음 캠프의 지표도 동일한 사유로 신뢰도가 낮아질 수 있다.
2. **설치 유도 온보딩 강화** — 설치율 78%, 푸시 프롬프트 노출 55%가 제약 지점이다. 첫 진입 시 설치 안내를 필수 단계로 배치하고 미설치 상태를 감지해 재안내한다. 목표: 설치율 90%, 도달률 85%.
3. **미사용 링크 정리** — 라이브 카드의 `schedule`·`versesTab` 링크를 제거한다.
4. **측정 분모 선확정** — 지표 정의서에 분자·분모·이벤트명을 함께 기재한 후 이벤트를 구현한다.
5. 일정·식단 등 나머지 정적 데이터도 관리자 페이지에서 실시간 편집할 수 있도록 확장한다.
6. GitHub Actions 기반 CI/CD 자동 배포를 구성한다.
