# 지표 정의서 (METRICS.md)

2026 로뎀나무교회 청년대학부 여름말씀캠프의 확정 지표와 그 정의를 기록한다. 수치만 남기면 다음 인스턴스에서 같은 혼선을 반복하게 되므로, **각 지표의 분자·분모·산출 조건**을 함께 적는다.

개요는 [README](../README.md), 의사결정 맥락은 [CASE_STUDY](../CASE_STUDY.md)에 있다.

## 0. 집계 기준

| 항목 | 설정 |
|---|---|
| 기간 | 2026-07-29 ~ 2026-08-01 (3박 4일) |
| 집계 단위 | **사람** — 닉네임 + 목장을 정규화해 uid 병합 |
| 운영진 | **제외** (`admins` 컬렉션 문서 ID = uid로 식별) |
| 기간 판정 | 기간 내 `app_open` 이벤트가 1건 이상 있는 사람 |
| 데이터 출처 | Firestore `events` 컬렉션 + 관리자 통계 대시보드 (`AdminStats.jsx`) |

기간 판정을 "첫 방문이 기간 내"로 잡으면 **신규 유입 코호트**가 되어, 캠프 전에 미리 등록하고 기간 내내 사용한 참가자가 제외된다. 분자(기간 내 이벤트)와 분모의 기간을 맞추려면 **활동 기준**이어야 한다.

## 2. 지표 정의

각 지표의 산출 방식이다. 분모가 무엇인지에 따라 값이 크게 달라지므로 반드시 함께 읽어야 한다.

| 지표 | 분자 | 분모 | 이벤트 |
|---|---|---|---|
| 앱 사용률 | 프로필 등록 사람 수 | 등록 명단 96명 | `users` 문서(nickname 보유) |
| 설치율 | `standalone` 상태 `app_open`이 1건 이상인 사람 | 앱 참여자 79명 | `app_open` (`standalone: true`) |
| 푸시 권한 허용률 | `result: granted` 사람 | 권한 프롬프트 노출 사람 | `push_permission` |
| 4일 리텐션 | 서로 다른 3일 이상 `app_open`이 있는 사람 | 앱 참여자 79명 | `app_open` (`day` 기준 distinct) |
| 공지 열람 (1회 이상) | 공지를 1건 이상 연 사람 | 앱 참여자 79명 | `announcement_view` |
| 공지당 도달률 | 공지별 고유 열람자의 평균 | 앱 참여자 79명 | `announcement_view` (`params.id`별 집계) |
| 조 편성 완료율 | 라운드 결과가 저장된 사람 | 앱 참여자 79명 ※ | `users.teams` |
| 온보딩 완료율 | 프로필 등록 사람 수 | 등록 명단 96명 ※ | `users` 문서 |

※ 표시된 두 지표는 사전 정의와 실제 분모가 다르다. 3장에서 설명한다.

## 3. 분모를 바꾼 두 지표

### 온보딩 완료율 — 방문자 → 등록 명단

**사전 정의**는 "앱을 연 방문자 중 프로필 등록을 마친 비율"이었으나, **사람 단위 방문자 수를 특정할 수 없어 그대로는 산출되지 않는다.**

미식별 uid 51개는 정의상 닉네임이 없어 병합이 불가능하다. 이 51개가 모두 기존 79명의 중복이면 방문자는 79명(완료율 100%), 모두 별개 인물이면 130명(61%)이 되어 **60~100% 범위로만 좁혀진다.** 어떤 이름을 붙여도 의사결정에 쓸 수 없는 값이다.

미식별 uid가 생기는 경로는 넷이며, 이 중 마지막만 실제 온보딩 실패다.

1. iOS는 Safari와 홈 화면 앱의 저장소가 분리되어, 브라우저에서 프로필을 만든 뒤 설치하면 새 uid를 받는다
2. 캐시 삭제, 시크릿 모드, 다른 브라우저
3. 링크만 받아 열어본 외부인
4. 프로필 등록 전에 이탈한 실제 방문자

따라서 분모를 **등록 명단 96명**으로 재정의했다. 미식별 uid의 정체와 무관하게 "참가자 중 미등록자는 최대 17명"이라는 상한이 성립하기 때문이다. 이 정의는 원래 물으려던 질문(참가자를 실제 사용자로 전환했는가)에도 더 부합한다.

### 조 편성 완료율 — 레크레이션 참여자 → 전체

**사전 분모**는 "레크레이션 참여자"였으나 실제 참여 인원을 기록하지 않았다. 전체 인원으로 대체했으므로 **실제 완료율은 70%보다 높다.** 다음 인스턴스에서는 레크레이션 시작 이벤트를 남겨 분모를 확보해야 한다.

## 4. 영역별 상세

### 4.1 확보 · 알림 퍼널

```
등록 명단 96명
  → 앱 프로필 등록 79명 (82%)
  → 홈 화면 설치 70명 (참여자의 89%)
  → 푸시 권한 프롬프트 노출 51명   ← 제약 지점
  → 허용 50명 (프롬프트 노출자의 98%)
```

| 단계 | 인원 | 참여자 79명 대비 | 등록 명단 96명 대비 |
|---|---|---|---|
| 앱 프로필 등록 | 79명 | — | 82% |
| 홈 화면 설치 | 70명 | 89% | 73% |
| 푸시 권한 프롬프트 노출 | 51명 | 65% | 53% |
| 푸시 권한 허용 | 50명 | 63% | 52% |

허용률 자체는 98%로 매우 높으나, **설치한 70명 중 51명만 프롬프트 단계까지 도달했다.** iOS가 홈 화면 설치 상태에서만 권한을 요청할 수 있기 때문이며, 알림을 받지 못한 인원의 다수는 거부자가 아니라 설치·프롬프트 단계에서 멈춘 사용자다.

프로필을 등록하지 않은 17명은 캠프 시작 이후 합류해 설치 안내를 받지 못한 것으로 추정한다. 온보딩이 행사 시작 시점의 일회성 안내에 의존한 구조였다.

**등록 토큰 60개** — 기기 단위 값이다. `tokens` 문서에 uid를 기록하지 않아 사람에게 귀속시킬 수 없으므로 허용 50명과 직접 비교할 수 없다.

### 4.2 공지

| 지표 | 값 |
|---|---|
| 발송 | 31건 (4일간, 하루 평균 7.8건) |
| 총 열람 | 925건 · 74명 (참여자의 94%) |
| 공지당 평균 열람자 | 17.0명 |
| 공지당 중앙값 | 13명 |
| 공지당 평균 열람률 | 22% |
| 📌 고정 공지 (1건) | 64명 = **81%** |
| 일반 공지 (30건 평균) | 15.4명 = **19%** |

삭제된 공지의 열람 3건은 평균에서 제외했다.

**고정과 일반의 차이는 4.2배다.** 상단에 상시 노출한 고정 공지는 81%에 도달했으나 푸시로 발송한 개별 공지는 평균 19%에 그쳤다. 도달을 만든 것은 푸시가 아니라 상시 노출이었다.

"94%가 공지를 열람했다"는 수치는 **4일간 아무 공지나 한 번이라도 연 사람**의 비율이며, 개별 공지의 도달과는 다르다. 두 지표를 구분하지 않으면 성과를 과대평가하게 된다.

**열람 상위와 하위의 성격이 갈린다.**

| 상위 | 열람자 | | 하위 | 열람자 |
|---|---|---|---|---|
| 📌 말씀캠프 자료실 | 64 | | 3일차 아침묵상 안내 | 8 |
| 비상 연락망 / 와이파이 | 38 | | 공동체 활동 안내 | 7 |
| 북토크 안내 | 31 | | 페스타 응원법 | 6 |
| GBS 2강 안내 | 30 | | 공동체 기도 안내 | 5 |
| 버스 탑승 안내 · 꿀팁 | 27 | | 공동체 활동 시작 | 4 |

상위는 전부 **행동이 필요한 정보**(연락처·탑승 시각·신청 방법)이고, 하위는 전부 **일정 리마인더**다. 그런데 일정 안내는 홈의 라이브 "현재 순서" 카드가 이미 수행하던 기능이므로 상당수 공지가 중복이었다.

## 6. 집계 수정 이력

최초 집계는 uid를 사람으로 간주하고 있었다. 익명 로그인 구조에서는 재설치·기기 추가마다 새 uid가 생성되므로, 등록 명단 96명에 대해 프로필 등록 123건과 방문 uid 172개가 쌓였다. 여기에 설치 집계 코드가 닉네임 미등록 uid를 분자에서 제외하는 결함까지 겹쳐 지표 전반이 실제보다 낮게 산출됐다.

세 단계로 바로잡았다.

| 단계 | 내용 |
|---|---|
| ① 사람 단위 병합 | 닉네임 + 목장을 정규화해 uid를 사람으로 묶음 (프로필 122건 → 79명) |
| ② 운영진 분리 | `admins` 컬렉션의 uid를 참여자 집계에서 제외 |
| ③ 기간 기준 수정 | "첫 방문이 기간 내"(코호트 정의) → "기간 내 활동이 있음"(활동 정의) |

| 지표 | uid 기준(최초) | 사람 기준(재산출) |
|---|---|---|
| 참여자 | 123 | **79** |
| 설치율 | 61% (75/123) | **89%** (70/79) |
| 4일 리텐션 (3일 이상) | 39% (68/176) | **81%** (64/79) |
| 공지 열람 | 73% (90/123) | **94%** (74/79) |
| 1일차 DAU | 146 | **69** |

**원본 데이터는 동일하며 집계 방식만 변경했다.** 특히 1일차 DAU 146은 설치가 집중되며 새 uid가 대량 생성된 결과였고, 이를 근거로 "4일간 55% 이탈"이라고 해석할 뻔했다. 실제로는 14% 감소였다.

## 7. 다음 인스턴스 측정 설계

이번에 확인된 문제를 사전에 막기 위한 항목이다.

| 우선순위 | 항목 | 조치 |
|---|---|---|
| 1 | uid ↔ 개인 매핑 | 설치 시 1회 코드 입력 또는 기존 프로필 복구 흐름. 사후 병합으로는 미식별 uid를 귀속시킬 수 없다 |
| 2 | 푸시 도달률 | `tokens` 문서에 `uid` 기록 (적용 완료). 기존 토큰은 규칙상 갱신되지 않으므로 행사 전 컬렉션을 비워 재등록 유도 |
| 3 | 조 편성 분모 | 레크레이션 시작 이벤트를 남겨 완료율 산출 가능하게 |
| 4 | 푸시 → 열람 전환 | `announcement_view`에 유입 경로(`source: push / toast / list`) 기록 |
| 5 | 정성 목표 제거 | "미확인자 없음" 같은 정의는 검증되지 않는다. 모든 목표를 분자·분모가 있는 형태로 |
| 6 | 세션 정의 | 앱 오픈이 아닌 30분 유휴 기준 세션 병합 검토 |

**지표 정의서에 분자·분모·이벤트명을 함께 적은 뒤에 이벤트를 구현한다.** 목표치를 설정하는 작업과 계산 가능한 형태로 로깅하는 작업은 별개이며, 이번에는 후자를 건너뛰어 온보딩 완료율과 조 편성 완료율을 사전 정의대로 산출하지 못했다.
